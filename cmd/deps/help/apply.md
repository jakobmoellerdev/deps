Resolves every dependency, prints the same report as `deps plan` on stderr, and writes the changed files, including `go mod tidy` output (`go.mod`, `go.sum`), regenerated `package-lock.json`, `npm-shrinkwrap.json`, `pnpm-lock.yaml`, `yarn.lock`, `bun.lock`, `uv.lock`, `poetry.lock` or `Pipfile.lock`, `Cargo.lock` updated with `cargo update`, `Gemfile.lock` updated with `bundle lock`, `composer.lock` updated with `composer update`, `Manifest.toml` updated with Julia's Pkg, `pubspec.lock` updated with `dart pub upgrade`, `MODULE.bazel.lock` updated with `bazel mod deps`, `mix.lock` updated with `mix deps.update`, `manifest.toml` (Gleam) updated with `gleam deps update`, `flake.lock` updated with `nix flake update`, `Podfile.lock` updated with `pod install`, `deno.lock` updated with `deno install --lockfile-only`, `jsonnetfile.lock.json` (and a committed `vendor` directory) updated with `jb update`, the files a Copier template update changes (`copier update`), and the `--hash` lines of requirements files (pip-compile/`uv pip compile` output is regenerated from its header command, other files get the new release's hashes from the index). An update of a pip-compile input (`requirements.in`) rewrites the input and regenerates every compiled file named after it. Post-processors run on temporary copies; a failed one drops that module's or lockfile root's changes and is reported as an error. An update a post-processor finds inapplicable (a compiled requirements file whose inputs do not admit the version, a Go module version that declares another path) is left out instead, and the other updates of its files are applied: it is reported as `skip    <file>:<line>  <name>  <from> -> <to>  (cannot be applied: <reason>)`, counts as skipped, and is no error.

A dependency with updates in several PR buckets contributes one update to the files: the newest non-major one, else the lowest major. Its other updates are reported with `, separate PR`, as is the lock file maintenance update (`lockFileMaintenance`), which only `deps run` makes.

The `postUpgradeTasks` of the config run in `--dir` after the files are written, in the order `run` uses, when `--allow-tasks` (or `$DEPS_ALLOW_TASKS`) allows each of their commands. Otherwise nothing is written and the error names the first command not allowed. With `files` globs, every other file below `--dir` the commands changed is restored to its state before them (ignored files are left alone).

The platform is only detected from CI environment variables. Locally, lookups run without a platform token unless one of the token variables is set (see `deps help environment`).

**Remote repositories.** `--repositories` (entries as for `deps plan`, see `deps help plan`) applies to clones deps makes itself; it needs `--into <dir>`, which is where each clone is kept, at `<into>/<owner>/<name>`, after the command. Each clone directory must not exist or be empty. The clones keep their `origin` and the checked-out ref, so `git diff`, `git commit` and a push by hand work in them. Post-processors and, under `--allow-tasks`, post-upgrade tasks run in the clone: that is repository code of a repository you may not have read. A failing repository is reported and does not stop the others (exit 1); `--report` holds the report of every repository with the counts summed over them.
